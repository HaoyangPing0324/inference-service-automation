# 配置、框架与算子联合自动调优

固定流程：**分析提出具体建议 → 配置/框架/算子联合调优 → chat_test → benchmark基线对比**。本文件是执行规则，不是已完成的性能优化案例。只更新Skill的请求不授权实际改代码、重启服务或跑测试；只分析结果也不自动进入调优。

## 1. 从分析生成可执行建议

PyTorch Profiler和Nsys分析均须在ANALYSIS.md给出可执行候选，而非只写“优化GEMM/减少空隙”：

| 字段 | 要求 |
|---|---|
| 建议ID、优先级 | 与后续计划、改动和结果一一对应 |
| 证据 | 实际文件/窗口/rank/shape/dtype/调用链及指标，区分热点与已确认瓶颈 |
| 改动层 | 配置、框架、算子，可多层联动 |
| 具体改法 | 参数旧值→候选值，或实际模块/函数/内核及拟修改逻辑 |
| 预期机制 | 为什么可能减少关键路径开销，不预先承诺加速幅度 |
| 风险与验证 | 精度/API/内存/调度风险，数值测试、chat、benchmark指标及回退 |

不能从trace确定具体文件或原因时，写“待定位/待验证”，列最小补充证据；不得编造源码行号或为了凑三类改动而强行优化。Nsys证据仍走官方Skill，硬件级瓶颈无证据不归因。

## 2. 结合官方指南制定联合方案

SGLang配置建议同时依据[官方Hyperparameter Tuning](https://docs.sglang.io/docs/advanced_features/hyperparameter_tuning)、对应安装版本CLI/源码和本次分析。记录访问时间、版本及适用前提；网页参数在旧版本可能改名或不存在，不能照抄。

重点按证据评估请求供给、实际batch、KV预算、调度保守度、chunked prefill、max-running-requests、CUDA Graph覆盖、TP/DP及合法后端。指南的离线吞吐建议不自动适用于在线延迟目标；不盲目增大队列或并发。精确检查点的权重格式与必需后端仍优先，不能因通用建议改坏模型兼容性。首轮no-prefix基线仍保留，任何cache/量化/并行等候选变更须在计划中明确，不能隐藏。

调优前形成AUTOTUNING_PLAN.md，确认：主目标与延迟/错误/精度约束、目标角色与允许改动范围、基线、一次候选预算及失败处理。缺少会影响执行的选择时询问用户。计划获得授权后，AI在范围内修改代码、构建并执行，不逐行要求批准；新依赖/新设备/超范围改动仍须询问。不擅自增加迭代轮数或不断重启找最优值。正常结束不自动恢复基线，也不把恢复基线捆绑进性能目标选项；记录当前实际运行版本。失败需恢复服务时先报告，按已有明确故障处理授权执行或询问用户。

### 每轮必须先写清计划

每轮实际改动前，在唯一的`tuning/<study-id>/AUTOTUNING_PLAN.md`填写可独立阅读的计划；模板不是已执行计划，不能用“见源码/按分析优化”代替具体策略。第一轮标明首次，后续获准轮次写清承接的基线/上一轮、保留/撤销/新增改动及原因。每轮计划不构成增加迭代预算的授权。

- 写明轮次与候选ID、当前状态、目标/约束、授权范围、候选数量、失败处理及分阶段预计耗时。
- 配置、框架、算子分别列：建议/证据ID、实际参数或文件/函数、旧值→新值或具体逻辑变化、预期机制、风险、数值/行为/加载/chat/性能验收。保持不变的一层也说明理由；没有依据不得硬凑改动。
- 预先记录每层希望改善的具体指标、预期方向及依据；只有可复核模型/历史或微测证据时才给定量范围，并注明局部或端到端、假设与不确定性。无法估计时写“未量化”，不强凑百分比；结果出来后不倒填原先预期。
- 固定可比条件：检查点、角色/资源、数据/seed、长度、并发/请求数/预热、采样/cache及计时协议；设计差异与负载差异分开。
- 列出基线验收→正确性→真实加载/chat→候选压测→对比/交付的顺序、待做/运行/通过/失败状态和证据路径。策略因新证据收窄或放弃时，保留原提议与修改原因，不事后把计划改成只有成功路径。
- `tuning/README.md`链接本轮计划和报告；原始分析的`profiling_results/ANALYSIS.md`链接具体计划，计划链接证据来源。分析写“建议”，计划写“本轮怎么做”，报告写“实际做了什么、效果如何”，不复制三份全文。

## 3. 默认只测一个联合候选

因完整benchmark成本高，默认把有证据支持的配置、框架和算子改动组成**一个联合候选版本**，不是为每一层各跑一轮完整benchmark，也不做默认网格搜索。无合理改动的一层明确“不变”。原始文件备份按baseline/framework和baseline/operators分类；配置基线另存experiment.toml/env快照、摘要和展开命令。

- 配置：先更新候选experiment.toml，再同步experiment.env与实际命令，保留基线快照。不可把模型采样或测试长度偷偷改成更容易的负载。
- 框架/算子：复用source-overrides.md的隔离挂载、版本检查和combined模式；代码冲突先合并，安装路径来自实际容器，不覆盖共享镜像。
- 每轮优化建立tuning/<study-id>/，基线与所有候选共用此轮目录，保存配置、源码diff/摘要、依赖/构建记录与角色映射；候选独立ID，不覆盖历史。
- 联合测试只能判断整个方案的效果，不能把收益分别归功于某个参数或内核。用户后续要求归因时，再确认是否增加单项消融测试及成本。

## 4. 先正确性，再性能

1. 对修改的内核执行预先确认容差的数值、dtype/shape/out/stride等测试；框架改动执行对应行为回归。chat不能替代精度/质量测试。
2. 在授权角色启动联合版本，确认候选配置真实生效、模块/内核实际加载，而非只在目录中存在。
3. 健康检查和官方格式的真实chat_test必须通过，保存输入/输出/退出码。失败不得进入正式benchmark或记为有效候选；按获准失败处理/回退策略执行，新增修复范围先问。
4. 若用户明确只做到chat，报告“功能通过、收益未验证”后结束；完整自动调优阶段在参数与预算已确认时继续一次联合候选benchmark。

## 5. 用benchmark判断效果

主判据是**关闭Profiler/Nsys后的同条件端到端benchmark**；Profiler/Nsys用于定位原因及必要的机制复核，不拿采集开销下的延迟当性能提升。内核microbenchmark可作低成本预检，但不能代替端到端收益。

先复用与当前目标可比的既有基线，避免重复跑。需要核对同一检查点、硬件资源预算、请求输入/数据与seed、ISL/OSL、并发/到达率、请求数、预热、采样/停止规则、冷/热cache测量流程、计时范围、客户端版本、实际token数及现场干扰。调优参数/源码本来可以不同，单独记为设计差异，不误判为负载变化；资源预算不同则只能标为不同资源方案，不能声称同资源提速。

无合格基线时先告知并确认补一次基线benchmark的成本；只有候选结果不能量化提升。不从Profiler请求日志、example数字或不同负载结果拼基线。

首次基线完整测C=1、2、4、8、16、32，不缩减；普通压测仍使用工程确认的完整CONCURRENCIES。优化调试默认只测C=1、8、32，一个联合候选执行一套三档，不为每层改动分别压测。每档N=5C、预热2（本协议合计205正式请求及6预热请求），其余长度、数据、seed算法、采样和统计协议沿用基线；用户明确另行定义的协议以其确认为准。

远端Linux宿主在实验目录执行`bash benchmark_test.sh`（或`full`）使用原完整档位；`bash benchmark_test.sh tuning`仅本次选用1、8、32，脚本内部进入client容器运行实际压测。不得把experiment.env里的完整CONCURRENCIES永久改成三档。调优计划已授权的prefix/cache等设计差异可用于tuning模式；full仍执行首轮no-prefix门禁，脚本模式不替代调优授权。

三档候选逐档与完整基线中相同C比较，不能把三档总耗时/总吞吐与六档合计相比较，不能外推未测C。规范化比较输入按单档拆分，conditions记录相同的C、seed、请求数及其他对照因素；从完整基线提取对应档位即可，不重跑全套基线。任一档缺失/不可比先报告并确认补测，不静默跳过；最终报告写明覆盖1/8/32，其他档位未复测。

不因“更稳妥”擅自重复多轮或多档搜索。一次观测可报告变化，但不能证明统计显著或稳定；若波动影响判断，报告不确定并询问是否加测。已获准多轮时可AB/BA交错并汇总中位数/离散度，不默认增加工作量。

根据用户目标同时检查output tokens/s或requests/s、TTFT、TPOT/ITL、尾延迟、成功率、实际token量及显存/资源；先确认使用均值还是P95/P99以及单位，不能混淆TPOT和ITL。吞吐提高但延迟超约束、请求失败或精度不达标时不判有效。默认不为每个候选重新跑两类Profiling；收益异常、需要验证机制或用户要求时，另行确认短窗补采。

可用scripts/compare_tuning_benchmarks.py对已解析结果作离线数值对比。它不启动服务、不运行压测，也不判断因果或统计显著。原始框架JSON需由AI依据真实字段映射到规范结构，保留原始文件及映射说明，不能猜测字段或丢掉失败请求：

```json
{
  "conditions": {
    "model": "confirmed checkpoint identity",
    "resource_budget": {"accelerator_type": "confirmed", "device_count": 1},
    "workload": {"confirmed_workload_fingerprint": "replace with actual resolved workload"},
    "measurement": {"scope": "end-to-end", "profilers": "off"}
  },
  "profiler_enabled": false,
  "variant": "baseline or candidate-id",
  "design": {},
  "runs": [
    {"total": 80, "successful": 80, "metrics": {"output_tokens_per_second": 100.0, "p95_ttft_ms": 200.0}}
  ]
}
```

上面数字仅示意格式，不是默认负载或实测。conditions必须完整记录已核对的对照因素；design记录允许改变的配置与源码版本。使用调用端已获准解释器，以脚本路径、基线和候选相对路径为参数，并显式给出`--objective`、`--direction higher|lower`、`--min-improvement-pct`；可重复指定`--guardrail metric:direction:max-regression-pct`。工具只做给定数据的校验和计算，不自动制定阈值、补数据或安装包。

### 每版压测验收后立即回写

基线或任一候选的本轮压测通过退出状态、成功数、实际token量和结果完整性验收后，**当阶段立即更新统一正式报告对应版本章节**，不得等联合调优结束才补写，也不能只写在tuning子目录。按版本标记三档/完整档位实际数据与单位、成功数和实际token量、从快照/脚本解析出的完整实际命令、配置差异、预计/实际耗时及核心结果位置；远端留存时明确服务器侧位置。不覆盖历史基线，不把局部微测当端到端结果。

同步本轮计划的执行状态、调优报告已实测部分、tuning索引和LOG，再向用户汇报该版压测完成。失败阶段也及时写失败点与未完成边界，不填性能占位数字。汇报前核对统一正式报告确有对应版本表格/命令、计划/报告链接可解析且状态一致；不能只承诺稍后同步。

## 6. 收尾

AUTOTUNING_REPORT.md写明建议ID→联合改动→正确性/chat→benchmark基线/候选及变化→约束→结论和不确定性，附核心结果相对路径。只有功能测试时不能写“优化成功”；一次联合对比不能声称各层独立收益。正常结束保持当前已验证运行版本，不安排额外的基线恢复/重载；需要切换由用户另行要求。保存基线证据不代表运行基线服务。更新统一正式报告实际设计与结果、源码验证报告和LOG，不覆盖基线历史；给出估时/实耗和可选下一步。

每轮完成报告还必须清楚回答以下三件事，主要用表格，失败/负结果同样保留：

1. **总体好了还是差了**：按实际测试档位汇总主目标指标及平均/尾延迟的基线→候选或变化百分比，注明单位、正负方向和成功率；结论结合用户目标、约束与代价，不仅列吞吐或只写“通过”。无显式SLO不编造达标结论。
2. **各层预期与实际**：配置/框架/算子逐项列原计划预期、依据、局部实测、端到端证据、与预期的差距及判断。联合实验未做消融时，单层贡献标“未单独测量/无法归因”，不能把联合收益分摊或把内核局部提速当服务提速；未重采的机制不能写已确认。缺关键路径占比时不虚构整体增益上限。
3. **下一轮方向**：提出优先假设、相对本轮保留/撤销/新增项、具体候选/对照、固定负载、评价指标/判读条件、缺失证据/风险及估时。区分推荐与执行，不因报告写了下一轮就创建实际运行、重启、补采或追加轮次；需要复验/消融时说明成本再获授权。

根分析和tuning索引只同步简短结论与本轮报告链接，详细预期/实测/后续策略集中在本轮报告；模板保持一致。

### 每轮结束的对话汇报：三部分，直击要害

用户不必打开报告才能知道做了什么、效果怎样。每轮结束（含负结果/失败）主动在对话依次给出：

1. **本次策略**：配置、框架、算子各一短句，只写关键旧→新及目的；未改的一层写不变。不要铺背景、贴长命令或罗列过程文件。
2. **效果**：一张百分比表，按实测并发/档位列主目标（默认输出吞吐）、平均TTFT、平均TPOT、P99 TPOT或实际已采集尾延迟的相对基线变化。写清吞吐增加更好、延迟减少更好；未测/无可比基线写未测/不可比，不填收益。附一句成功数，避免只报成功样本。
3. **结果分析**：用2–3个短句回答总体变好/变差/取舍、主要代价及最关键不确定性。联合实验不强行归因单层；具体机理/预期对照实测留在详细报告，不把全文搬入聊天。

末尾紧凑附核心报告可点击路径、原预计/实际耗时；合乎当前状态的下一步只给一条建议及估时，不自动执行。Skill维护的完成说明一句即可，不挤占上述实验结论。不隐瞒退化，也不以“功能通过”代替性能结论。

## 优化实验归档

本节baseline/candidate的configuration/source/validation/benchmark/comparison是远端完整工作归档；本地只取project-contract定义的干净审阅子集，单候选为experiment.toml、实际改动source/、修改说明及必要轮次报告，不回收原始压测或空目录。


仅在用户授权优化轮次后，才按需在实验目录创建`tuning/<study-id>/`，普通部署/压测/采集不创建`tuning/`。计划与报告骨架从Skill的`scripts/templates/inference-project/tuning/templates/`或PD对应模板读取，直接填写到实际study，不在实验复制`tuning/templates/`。`tuning/README.md`只有需要索引实际轮次时才创建，记录目标、状态和报告链接；不散落根目录或覆盖已有Profiling分析。

```text
tuning/
├── README.md                         # 历次优化索引
└── <study-id>/                       # 本轮全部实验与分析
    ├── AUTOTUNING_PLAN.md            # 目标、预算与修改范围
    ├── ANALYSIS.md                   # 本轮证据与具体优化建议
    ├── AUTOTUNING_REPORT.md          # 最终逐档对比与结论
    ├── baseline/                    # 基线配置、命令、压测原始结果
    └── candidates/<candidate-id>/    # 配置、源码diff、验证、压测及对比
```

每个版本的configuration/、source/、validation/、benchmark/、comparison/按需创建，只收纳实际生成的内容。基线源码仍按framework/operators分类；活动source_overrides引用到候选的明确版本，归档不能误改运行挂载。原始Profiler/Nsys结果仍在原处，用路径、run与SHA索引引用，不重复复制大文件。远端结果按用户约定留存或回收，报告必须说明位置；本地仅有目录骨架不算实验完成。

### 轮次、版本与新增Profiling的归属

一个study目录代表完整一轮，包含基线、候选、分析和报告，不只是“优化后结果”。新一轮用新的唯一study-id；同轮已获准的多个候选用不同candidate-id，源码/设计变更后不能继续写入旧版本冒充同一方案。不能因本规则默认增加候选或轮次。

- 普通、非调优Profiling仍放实验根的profiling_results/，不迁移已有结果。
- 对某轮基线/候选补采时，先核对实际加载的配置、源码版本和角色，再确定所属study及version；不按“最新目录”猜测。归属不明确先询问，采集授权/参数仍单独确认。
- 新产物放本轮baseline/profiling_results/或candidates/<candidate-id>/profiling_results/，其下按当前time协议为profiler或nsys/C<C>/capture/{single或prefill、decode}/；历史steps结果仍保留原initial/after-prerun布局，不混写。分析写该版本profiling_results/ANALYSIS.md，不覆盖实验根原始分析或另一版本。
- 在对应MANIFEST/窗口元数据记录study、version、源run与配置/源码摘要，使本轮benchmark和Profiling能关联同一方案；不能把旧基线trace复制一份就称为候选采集。复用历史证据只链接其原路径/run/SHA。
- 远端原始捕获仍用现有server/profiles/<unique-run>/避免干扰框架；版本目录保存核心归档或指向源run的清单。用户选择只留服务器时也维护此归属索引，不强制重复复制大文件或下载。
- Torch回收保持--project为实验根，额外传--result-owner tuning/<study>/baseline或tuning/<study>/candidates/<id>。现有版本目录必须已建立；同一C替换只限该版本/工具，验收后才替换，不影响基线、其他候选、轮次或另一工具。Nsys按相同归属整理。

## 远端工程与本地交付

本轮配置、源码、baseline/candidate、构建及验证工作目录均留在远端；design远端编辑并封存，execute验证，analyze分析，经二级协调。只有必要的设计表、已要求的采集/分析及已开展轮次报告回收本地tuning/<study>/；benchmark原始数据默认留远端，指标和对比直接写报告；本轮实际修改/新增的框架和算子文件另按project-contract回收至source/framework、source/operators，并写一份修改说明；不复制未改动源码、构建缓存、调度日志或整份候选工程。统一<title>.md仍由design从实际脚本完整还原，自定义源码嵌在Markdown中，报告不依赖源码附件也能复现，本地source副本另外用于查看和审阅。

实际被替换文件的修改前原件也要回收至tuning/<study>/baseline/source/{framework,operators}/，仅保留本轮涉及文件；原文件名和内部相对层级不变，修改版在source/对应位置。多候选共用同一真实基线时只存一份，基线不同则按候选隔离并说明。原件必须在修改前从实际运行版本冻结，不能事后猜造；新增文件没有原件，在修改说明中标为新增，不建空基线文件。
