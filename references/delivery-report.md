# 正式报告：实际命令、完整实现与结果

唯一正式报告为实验根`<title>.md`。它是实时维护的单文档复现说明：只收到这个Markdown的人，按文内流程和给定环境即可执行，不能要求作者另外提供工程文件或解释遗漏步骤。

## 强制写作形态

- 首次写作前按根Skill导航选读同拓扑example的目录、报告和相关脚本，借鉴“准备/容器→服务→对话→压测→采集→优化”的直接写法。平台、模型、拓扑不同可以增减子节，不能机械复用其他平台参数。
- 正文以流程标题、完整代码块、必要操作指引和结果表构成。每个代码块前仅写执行主机/容器或文件保存位置；参数含义优先用代码内简短注释表达。只有影响正确执行或结果解释的信息才写独立句子。
- 标题后直接进入第一个已开展阶段；不写背景导语、模型与拓扑复述、报告整理说明、版本核验长段、示例免责声明、目录清单、文件数量/总字节数/摘要一致性或反复的成功边界。必要环境值直接体现在准备命令、注释和参数中。
- 不在报告链接、引用其他Markdown、设计依据、验收文档、ANALYSIS、LOG、MANIFEST或Skill来补步骤。来源和核验材料在工程维护，报告正文不设证据索引/参考资料章节。公开镜像/模型/数据是第三方运行依赖，应给出明确来源、版本与准备方式；不要求把权重或第三方仓库全文嵌进报告，也不能编造未知下载来源。
- 不调用文中未给完整定义的自定义脚本、配置、模块、patch或回调。所需代码一律按“保存为准确路径→完整源码→执行命令”呈现；源码只定义一次，后续可用同一文件的完整调用。

## 实时维护与流程顺序

顶层按“1. 启动服务→2. Baseline压测→3. Profiling→4. 优化1→5. 优化2……”排序。准备、容器、各机器/角色、健康检查和对话归入启动服务；不同负载为压测子节；Profiler和平台适用的其他采集工具为Profiling子节。

只写实际已开展阶段，到哪一步维护到哪一步。尚未开展的后续阶段不预建标题、不写“未执行/计划/待交接”段落或空表。正在进行的阶段先写已确认实际执行的步骤，有有效结果后立即填在对应命令之后。既有模板的编写提示与未用章节必须移除。

按复现流程组织，不按日期、重试、上传、暂停恢复、报告修订或计时流水组织。采集因用户要求先于Baseline发生，也不改变逻辑阶段顺序；没有Baseline就不填该章。优化确已开展才写策略、必要实现与验证、候选压测和对比结果。

## 从实际脚本还原命令

1. 读取本轮实际运行的脚本、配置快照和调用记录，展开`source`、数组、变量、循环、角色覆盖和入口包装，得到当时真正执行的命令。镜像、模型、设备、挂载、环境、精度、并行度、cache、数据、seed、端点、请求数与采集窗口语义必须一致。
2. 允许换行排版、把历史内联实现单列为文件，或将纯配置包装展开成等价原生命令；不在写报告时改参数、换接口/数据源/镜像、设计新控制器、加入新验证方法或生成一套更漂亮但未执行的流程。需要修正执行逻辑时另走实验修复授权；报告只写已验证边界。等价呈现的核对结果写工程日志，不往正文追加整理声明。
3. 容器、服务、客户端和调用端的执行位置必须明确。所有目录创建、文件保存、挂载、进入容器、服务切换、后台运行及依赖准备给可直接执行的命令；仅列某个本机image ID不算给镜像来源。必要脚本须从Markdown创建，不依赖原工程预先存在。
4. 多机流程逐项写出源主机/容器、源文件、目标主机/目录与完整复制命令。禁止“先复制到另一台机器”“同步相关文件”“按前文配置启动”等省略。不得假定PD客户端、Prefill、Decode共享本地目录；跨机workload、控制器、校验脚本与结果都须可达。
5. 自定义Python等实现放独立语言代码块，再给调用；不使用长`python -c`、heredoc、cat/echo生成器把源码藏在命令字符串中。第三方框架补丁可提供完整确定性生成程序，包含源版本、全部修改与必要摘要校验；新模块与测试仍完整给出。
6. `experiment.toml/env`等内部设计/布线不整份粘贴到正文；展开其实际值进入命令。仅在某自定义实现确实读取独立配置且不能等价展开时，给出该必要配置完整内容和创建位置。

## 结果和异常

- 命令后紧接实际回复、指标表或必要验收结果。压测表包含实际并发、成功数、吞吐、TTFT/TPOT及已采集分位数；TPS/GPU注明整套设备分母。优化紧接候选结果给原值/变化百分比表，结论仅一两句说明收益与代价，不添加未经执行的后续计划。
- 不把请求成功写成采集完整，不把已有文件写成设备/阶段覆盖已验证，不给空结果填数字。example缺少对应实测时只保留“结果：未测。”，实测状态集中在example的LOG/元数据维护，不在报告放长免责声明。
- 未解决失败在失败步骤后最多一句说明实际阻塞；完整旧失败脚本、重试记录、PID、时间戳、校验器流水、文件摘要、回收噪声和不影响性能结论的文件统计留工程证据。失败后已有验证成功的最终步骤则呈现最终步骤，不能隐去影响结果有效性的限制，也不能把新改法当已执行。
- 核心trace或`.nsys-rep`路径可作为结果列出，完整SHA与逐文件大小留在工程。正文不得用“详见结果文件/分析文档”代替应当直接给出的指标和结论。

## 交付前检查

沿Markdown从头模拟：从给定基础硬件/驱动及第三方依赖出发，每个自定义文件能否仅用文内代码创建？每条调用/导入/挂载的文件是否存在？PD文件是否确实到达目标节点？有无依赖外部文件补参数或源码？所有命令是否对应本轮实际输入，结果是否属于该版本？

删除每一句不影响执行和结果理解的话。解析代码与Shell语法，从原结果复核表格和百分比，运行项目校验器；静态通过不表示重新部署、采集或测量。正式报告的最终可用性仍须完成上述逐步审阅。
