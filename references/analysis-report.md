# Profiling 分析报告写法

分析口令或已授权的完整自动调优流程才更新实验 `profiling_results/ANALYSIS.md`。先说明分析对象与工具来源：PyTorch trace统计和官方Nsys Skill证据分开；官方 `profiling/nsight-systems/` 不修改。缺少原始数据时明确限制，不分析example中的占位文件。分析应产出可供配置/框架/算子联合调优执行的具体建议；只分析不自动修改或重启。

上述路径对普通实验相对实验根；调优版则相对tuning/<study>/baseline或candidates/<id>，由当前分析对象决定。候选新采集的分析不得覆盖根目录旧基线分析，跨版本比较明确标出各自来源与配置。

## 默认结构

1. **范围与文件**：简表列模型/拓扑、负载、窗口、实际batch和最核心可打开文件；指出示例是否只含占位。解释每种图用于回答什么问题。
2. **怎么看图**：先解释时间轴/跨度与层级，再用“轨道或thread → 含义 → 本次实际用途”表区分CPU进程/线程、GPU设备/CUDA stream、kernel和阶段标记。对用户正在看的具体图，按真实metadata和事件逐一解释主要轨道；未知线程用途写未确认，不凭编号猜测。同名进程可在CPU/GPU分别显示；GPU stream不是CPU thread，stream编号不是固定算子角色，重复块不是天然等于layer。
3. **现象、分析与结论**：每行一个问题，列“现象/数据 → 解释 → 结论及证据”。PyTorch与Nsys分小节，不堆叠长段落。数字写单位、分母、窗口及rank/设备范围；不要把单rank当全机，把跨GPU累计值当墙钟，把覆盖率当SM利用率，把API等待当CPU计算。空白区先对齐同一时段的其他stream和CPU调用；未核实不归因。
4. **总结与优化建议**：最后明确已确认热点、尚未证实的瓶颈、按优先级排列的改进候选。建议表写“针对什么问题 → 尝试什么 → 用什么指标验证”，不罗列无关调优开关，不承诺加速比例。没有证据确认唯一瓶颈时直说，不能为了给结论而猜。调参/重采仍须原有授权，不因写建议而执行。

## 简洁但可复核

- 优化建议按`autotuning.md`列建议ID、证据、配置/框架/算子分类、参数旧值与候选值或实际模块/函数/内核、具体改法、预期机制、风险、正确性与benchmark验收指标。无法定位时标待验证，不只写“优化算子”。SGLang配置同时依据对应版本官方Hyperparameter Tuning与本次证据，不照抄通用数值。
- 建议默认组成一个联合候选，以节省benchmark成本；无证据的一层可不变。chat只证明功能；关闭采集的同条件benchmark判断端到端收益，Profiling解释机制。不要将kernel变快直接等同于服务加速，或把联合方案收益归因给单项。
- 获准进入调优后，根分析保留具体建议及证据，并链接`tuning/<study-id>/AUTOTUNING_PLAN.md`的本轮具体实施策略；每轮计划分别写明三层改动/不变项、风险与验收状态，最终报告记录实际效果。不能只在调优子目录补建议却让根分析保留过时的结论，也不在三处重复整篇报告。
- 已完成实验的详细报告按`autotuning.md`补齐逐档总体好坏对比、三层原预期与局部/端到端实测、差距与归因边界、具体下一轮建议。根分析只同步关键结论和链接，不能把后续建议写成已经执行。

- 结论用短句，主要比较用表格；长kernel名称用易懂简称，并在证据处保留可定位名字或来源。
- 主体只保留支撑判断的数字；原始facts、完整统计和日志用相对链接供追溯，不粘贴JSON或CLI流水。不重复同一限制多遍。
- C为请求并发上限，实测batch须单列；预运行后窗口不自动称稳态。DSPARK等多阶段实现区分DRAFT与VERIFY，不把step等同token。
- Nsys的报告健康、活动GPU及数值按官方Skill的gateway验收；内核硬件瓶颈需Nsight Compute，通信/重叠等域结论遵守官方recipe证据要求。明确“确认/推断/待验证”，但避免每句机械加标签。
- 图不在手边时可以提供对应文件的读图表，不虚构截图、颜色或轨道用途；局部时间段统计标注文件和近似时间范围，不能推广至整份trace。
- 通用模板、example与真实报告采用同一骨架；example不复制大型结果，不把真实机器路径或本次stream编号写成通用规则。
