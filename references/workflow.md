# 执行流程

## 0. 阶段参数门禁

每次只准备用户要求的当前阶段。部署按根Skill“部署优先”执行：使用已配置模型、镜像和设备，轻量检查无资源冲突后直接启动；迁移技术参数在现有授权内自行选择，不先做全量参数/兼容性审计。

- Profiler/Nsys默认只采一个中间time窗口：预热2后持续最多C个在途，完成4×C正式请求后采capture_seconds（默认15秒），停止采集后继续完成至少C请求再结束负载；不固定N=5C，不采initial/after-prerun。可选最短预运行时间默认0秒。P/D步数仅事后统计，max_requests触顶即失败；single保留混合trace，PD并发控制P/D端点，默认不采Router GPU。

- 部署只需能定位检查点、可用镜像、目标主机/设备、部署方式和运行目录；命令按已有配置/平台入口生成，无精确教程则直接采用合理迁移配置试跑。
- benchmark 至少需要输入/输出长度、并发档位、每档请求数或其明确计算规则、预热次数、数据集/生成方式和结果目录策略。
- benchmark、PyTorch Profiler 与 Nsys 的 tokenizer 使用容器内已挂载检查点的 `MODEL_PATH`。请求中暴露给服务的模型名只用于 API 的 model 字段，不能兼作 tokenizer 来源并触发网络解析；仅当 `MODEL_PATH` 中 tokenizer 文件不完整或不可读时暂停并询问。
- 分析至少需要明确的本地 run 目录；存在多个候选 run 且用户未指定时必须询问，不能默认选择最新或文件最大的一个。
- 清理必须能从配置和 `LOG.md` 唯一识别本实验对象；有归属不明对象时保留并询问。

只有缺少用户意图、超出资源/成本授权、需新增依赖或可能影响他人时才询问。启动报错由execute按错误定位和范围内修正后再试，不把每个技术选择交回用户审批；无新证据时不原样重复失败命令。

## 1. 最小准备后直接启动

1. 沿用本实验environment.toml与已有用户参数；已明确的目标和卡型不重复询问，不因工具未显示型号后缀要求用户再次证明。
   镜像尚未由用户选定时，execute按common-operations只读列出现有相关镜像与推荐，经二级/一级询问选择；用户明确选定或授权AI选择后才运行容器。模板默认或AI候选不算用户已选；新镜像拉取须在授权内。
2. execute对本次拟用设备、端口和容器名做一次窄检查，确认不会覆盖/抢占他人任务即可。不检查所有候选服务器，不逐项审计驱动、芯片、镜像内部依赖和模型每个文件；必要信息由启动日志提供。
3. 只有实际冲突才展开进程/容器归属、需求/可用/缺口和最小释放方案，交二级汇总给一级。未获授权不清理他人对象。没有冲突就继续，不重复生成资源证明材料。

## 2. 从已有平台入口取命令

1. design先读platforms/README.md、对应平台sources.md及与本次部署有关的experience条目；例如Ascend使用platforms/ascend/sources.md。直接打开其中官方文档/仓库并定位模型/版本，不先全网搜索。只有入口失效、模型/版本未覆盖或出现具体错误时针对缺口搜索，不以换个搜索关键词替代读取已收录导航。
2. 复用已有工程/镜像和参考启动方式。缺少精确组合时按迁移规则选合理初版，在已有授权范围直接启动，不等待完整兼容矩阵、证据表或迁移候选审批；不声称类比配置是精确官方复现。
3. 保留用户固定参数和首轮关闭prefix cache的规则，未覆盖项保留框架默认/自动识别，不强行指定量化或backend。已有参考命令/模型元数据够用即启动，版本与生效值随启动日志按需补记。
4. 启动出现缺权重、配置、tokenizer、设备挂载、版本/CLI或显存错误，再只查相应问题并修正。需要新增安装/下载时按已有授权执行或询问，不为预防所有可能错误先逐项检查。
5. 多机只核对实际参与角色的模型路径；发生缺片、版本差异或加载异常时再比较清单/必要摘要，不默认对全目录逐文件校验。采集与分析相关平台经验等进入对应阶段再读。

### 环境依赖缺失

遵循总入口的全阶段先询问规则，不限于Python包：任何缺少的环境、软件、工具、库、数据或模型文件都不得自动补装/下载。先确认用户指定的执行环境，再提出有明确范围与来源的方案；工具自身建议的安装命令不能代替用户授权。报告验收/分析可在采集容器外的获准环境执行，但必须验证报告可读、工具与解释器兼容；出现工具专用解释器冲突先询问，不自行更换环境。

任一步骤出现 `command not found`、模块导入失败、动态库缺失、CLI 子命令不可用或版本不满足时：

1. 先确认失败发生的准确环境（本地解释器、目标 SSH 主机、宿主机或具体容器），不要把一个环境的缺失推广到其他环境。
2. 在同一条回复中告诉用户依赖名称、用途、失败命令/关键错误、阻塞范围和不受影响的后续工作。
3. 给出与该环境匹配的最小安装或修复方式，并说明是否会修改共享环境；如果存在无需安装的可靠替代方案，一并列出其能力边界。
4. 用户未明确授权前不执行安装、升级、降级或环境重建。等待选择期间可以继续独立且安全的步骤；使用替代检查时必须如实标注，不能声称原工具校验成功。
5. 模型下载遵循common-operations的ModelScope优先规则，由对应execute执行；原HF模型采用该首选站不属于需要再次批准的临时换源。该站无精确模型/版本或不可访问时报告缺口，其他依赖/数据源不得自动切换。模型/tokenizer已挂载时使用MODEL_PATH，无需重复询问；内容不完整时只定位实际缺失项，补下载仍按已有授权范围处理。

## 3. design直接维护远端工程

本地先保留已填写environment.toml。design依据其workspace_dir和title，在本次选定源节点建立/复用远端工程；脚本、experiment.env、内部日志和coordination都在远端编辑，不能把本地交付目录当源码主副本。

首次需要模板时，只把生成器及所需模板、校验工具作为一次性引导材料送到远端工程coordination/bootstrap。将环境配置放在实际远端工程/environment.toml，然后在该远端已有Python环境运行生成器`--remote`模式；不在本地生成完整工程再循环上传。现有已完整工程不覆盖式重生成，直接定点编辑。模板选择和模型适配继续遵循单服务/PD隔离，当前部署只填启动/chat相关命令。

远端experiment.toml记录显式设计项；发布阶段后回收其最新副本供用户查看修改。用户修改本地表时，明确请求应用后再由design对比差异、同步到远端新版本，并重建experiment.env；运行中冻结版本不自动改变。报告由design依据远端真实脚本维护并回收本地。

## 4. 版本发布、多机同步与本地交付

design在远端隔离副本修改，静态核验后指定冻结版本与角色入口，经二级交execute运行；所有本次相关sh在运行前确保可执行。多机在实际参与节点间只同步必要的相同版本文件，不复制他人目录、模型或全部工程。执行报错由execute隔离试修，验证成功经二级交design固化远端真源，无“先回写本地再上传”要求。

本地回收只按project-contract“远端真源与本地交付”白名单，缺省不回收脚本/experiment.env/LOG/coordination。文件在远端封存后才传输，先暂存、核对范围/大小/摘要再发布，不用整目录镜像或删除旧交付。大型原生结果保留整个本次产物目录，可按原结构打包入结果目录，不把零散临时文件放本地根。

部署校验在实际远端工程运行`validate_inference_project.py <REMOTE_PROJECT_DIR> --remote --stage deployment`，只验证当前启动/chat所需项；未开展benchmark/profiling不阻塞部署。分析已有结果无需先下载，按授权在远端离线处理。

## 5. 部署与首轮 benchmark

1. 只在已分配主机的宿主机上创建容器。记录实际镜像 digest、容器名、端口和设备范围。涉及既有容器的停止、删除或端口释放时，按 [operations/common-operations.md](operations/common-operations.md) 的准确对象语义和统一验证步骤执行。
2. 启动服务前再次确认 `PREFIX_CACHE_MODE=disabled`，并核对禁用参数的证据。
3. 启动服务并等待健康检查，不用固定 sleep 代替健康检查。
   - 若日志在 CUDA Graph 捕获阶段报显存不足，先核对各设备总显存、失败时可用显存、失败分配大小和进程归属，根据实际缺口计算，不推荐固定目标值。统一字节单位，单卡当前分配缺口 `D=max(0,申请量-可用量)`；核实该框架版本的显存比例分母与预算方式后，若预算近似按总显存T线性变化，先算 `候选比例≈当前比例-D/T`，再在候选比例上额外减去 `0.01`（一个百分点，非相对下降1%）留作安全余量，即 `新比例≈当前比例-D/T-0.01`。若配置只保留两位小数，向下取整，不能向上舍入削减余量；多卡按各卡计算，以约束最紧、要求比例最低的设备为准。这是“按缺口计算后再下降一个点”，不是每次从当前值固定减0.01。单次OOM仅给出当前分配缺口下限，后续Graph捕获仍可能需要更多显存；该余量和计算值不保证成功，也不能将缓存预算变化直接当作等量可用显存。无法确认预算关系时明确不确定性，提出试验方案，不伪造精确计算结论。用户已授权启动并遇错修正时，可在既有资源及固定工作负载范围内据此调整重试，不逐次询问；不得改用户固定约束或处理他人进程，只有超出授权或无法满足目标负载时询问。正式报告和日志记录原值、各次新值、缺口计算、额外0.01余量、取整方式及验证结果。
4. 分两层验证服务，不混用判据：
   - 在线探活：检查健康端点和模型列表，只判断路由、端口、worker 注册和模型暴露是否正常。
   - 问答验证：进入 client 容器执行 `chat_test.sh`，发起一次真实生成请求。优先逐项复用精确检查点官方示例的 endpoint、输入格式、提示词和采样参数；精确官方资料没有问答示例时，复用对应 example 的请求和提示词（例如参考脚本中的 `Hello`），仅适配服务地址与模型名。不要另造 `Reply with exactly: ONLINE` 一类提示词来代替参考问答。
5. 生成 `chat_test.sh` 前确认模型输入约定。模型具有官方 chat template 时使用与官方示例一致的 `/v1/chat/completions` 请求；没有 chat template 时，先读取检查点附带的 encoding/README 或模型卡，按其官方编码方式构造输入，或者使用其官方 completion 示例。不得把 chat 风格指令直接放入未编码的 `/v1/completions`，也不得把这种请求产生的随机续写仅凭 HTTP 200 判为 chat test 成功。
   endpoint 和输入格式按以下证据顺序确定，不能根据模型名称或另一个模型的脚本猜测：
   1. 精确检查点针对当前框架/版本给出的官方服务请求示例；有示例时沿用其 endpoint、字段和编码方式。
   2. 检查点的模型卡、`tokenizer_config.json`、tokenizer 文件和自带 encoding/template 文档。存在兼容的 chat template 且当前服务版本确认支持时，才使用 `/v1/chat/completions`。
   3. 检查点明确不提供 chat template、但提供官方消息编码器时，用该编码器把 messages 转成 prompt，再调用官方支持的 `/v1/completions`；返回文本再按同一套官方解析器处理。
   4. 只有框架或检查点官方资料明确要求时才使用 `/generate` 等原生接口，并记录其请求 schema。
   5. `/v1/models`、OpenAPI 路由列表或一次 HTTP 200 只能证明接口存在，不能证明模型的消息模板兼容；最终必须用官方示例或参考提示词完成一次可解析的实际生成。
6. chat test 至少校验 HTTP 成功、响应中的模型名、非空生成内容和响应结构；若官方示例定义了额外语义或格式，再按其要求校验。除非官方示例本身要求确定输出，否则不对开放式生成做逐字相等断言。保存实际请求和完整原始响应，正式报告展示提示词及模型回复，`LOG.md` 记录接口、退出状态和判定依据。
7. 进入对应容器执行服务、chat test、benchmark。宿主机脚本只允许通过容器运行时调用容器内脚本。首轮其他服务参数保持官方教程值。
8. 保存原始JSON/JSONL和程序日志，完整命令与结果写正式报告；LOG只记阶段有效性、关键异常/设计决定及报告入口，不复制每条命令和检查输出。

部署完成时，在对话中给出用户设计表 `experiment.toml` 的准确本地路径和来源，并汇报实际模型/镜像/框架、角色规模、TP/DP/EP/PP、总设备数、量化/后端、speculative/draft、显存比例、prefix/KV cache、chunked prefill、本地适配及 chat test 结果。IP、端口、路径和容器名仅在异常时报告；不得只回复“服务在线”。

首轮完成后，后续设计调整先修改 `experiment.toml`，再同步更新内部 `experiment.env`。每次改动记录旧值、新值、原因和结果目录，避免覆盖基线；不得只改内部文件而让用户设计表失真。

设计表按configuration.md“按阶段记录设计参数”维护，只记录本阶段显式设置和实际已知值，不为补全内部默认项阻塞启动或交付。

## 6. Profiling

顺序与示例保持一致：PyTorch Profiler → Nsys 启动 → workload 采集 → Nsys 统计/报告。

- 使用当前模板的后台PID、exitcode、time控制与验收实现；示例历史记录不决定当前默认协议。
- 默认走无Hook原生连续采集；核实精确版本接口，不兼容时报告，获准后再做最小适配。
- 每个 TP rank 必须有窗口摘要；期望 rank 数来自 `PROFILE_TP_SIZE`，不能硬编码为 8。
- time本地结果按工具/C<C>/capture/下single混合时间线或prefill/decode角色组织，历史steps布局保留。
- “profiler”只执行 PyTorch Profiler；“nsys”只执行 Nsys；只有“profiling”才依次执行两者。每次采集使用唯一 run id，不能把旧产物混入本轮验收。
- PyTorch Profiler 完成后，在每台参与角色的节点验证其期望 TP rank 与角色窗口摘要，再由design按交付白名单把本轮必要的 `*.trace.json.gz`、窗口摘要、workload 参数、benchmark 原始输出和日志复制回本地 `profiling_results/profiler/C<C>/`；只有本轮启用 native `key_averages` 时才要求并回收对应算子表。多机角色按主机或角色保留子目录，避免同名覆盖。只有本地文件数量、大小和远端一致且必要摘要校验通过，才算“profiler”完成。
- Nsys 完成后，把每个参与角色本轮生成的 `.nsys-rep`、采集日志和 workload 元数据复制到本地 `profiling_results/nsys/C<C>/`，同样按主机或角色隔离并核对文件。生成 stats 不替代保留原始 `.nsys-rep`。
- 采集完成回复先说明实际负载、持续时间、角色控制时差、实际请求数、阶段覆盖与batch，再列核心文件；不把配置时长或计划步数当实测。

正式交付只维护`<title>.md`，完整遵循[报告规则](delivery-report.md)：启动服务→Baseline压测→Profiling→真实优化轮次；chat为启动服务子节，PyTorch/Nsys为Profiling子节。源码按文件完整展示，再给独立调用；所有命令从实际版本展开。详细分析与计划/轮次报告保留，不把它们全部并入正文。历史双报告不再是新工程的格式真源。

## 7. 分析与结论

- PyTorch trace：运行项目中的 `client/analyze_torch_trace.py`，比较各 rank、prefill/decode、GPU 活动、通信和长尾。
- Nsys：加载 `profiling/nsight-systems/SKILL.md`，先完成其平台 bootstrap，再对具体 `.nsys-rep` 使用它提供的 report facts/recipes。不要只根据 `*.stats.csv` 推断复杂利用率或通信重叠。
- 在 `profiling_results/ANALYSIS.md` 中区分事实、推断和待验证项；每个数字注明来源文件或命令。
- “分析 profiler 结果”只读取已有 PyTorch trace、窗口摘要以及本轮实际存在的 key averages，生成或更新 `ANALYSIS.md` 的 PyTorch Profiler 部分，不启动新采集。没有 native key averages 不阻塞分析；需要算子聚合时只能给出明确标记为离线近似口径的统计，不能冒充 PyTorch 原生表。
- “分析 nsys 结果”必须先加载 `profiling/nsight-systems/SKILL.md`，对已有 `.nsys-rep` 完成其 bootstrap、facts/recipes 和证据流程，再生成或更新 `ANALYSIS.md` 的 Nsys 部分；不能只看 `*.stats.csv`。
- “分析瓶颈/分析 profiling 结果”按 PyTorch Profiler → Nsys 的顺序执行上述两种分析，并增加综合瓶颈部分；保留已有其他部分，不覆盖历史证据。

## 8. 项目暂停或结束

用户明确说“项目暂停”或“项目结束”时，按配置和 `LOG.md` 枚举本实验在所有目标主机上的准确容器名、PID、端口与设备，随后停止并删除全部可追溯的本实验容器；仍有脱离容器但可证明属于本实验的进程时一并结束。清理后统一验证容器不存在、端口释放、相关设备进程消失。

- 不删除本地或远端项目文件、模型、镜像、挂载目录、benchmark/profiling 结果和日志。
- 不结束 `rootlesskit`、容器运行时、归属不明进程或其他任务容器。
- 某对象无法证明属于本实验时保留并报告，不为实现“全清”扩大影响范围。
- “暂停”和“结束”在运行时清理范围上相同；两者都保留文件，方便恢复或复盘。

## 9. 完成判定

只按用户本次授权阶段判定：部署到健康与真实chat；压测到所需档位结果可解析；采集到原生产物/窗口验收及所需回收；分析到相应证据与结论；优化按该轮已授权验证和比较。各阶段由design及时更新已实际开展的正式报告。未请求的benchmark、profiling、分析和优化不作为完成条件，也不列成未完成待办；真正请求但失败/未做的部分才说明边界。
