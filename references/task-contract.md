# 阶段任务契约

本文件维护用户口令、阶段完成边界、耗时与跟进、核心产物汇报及缺参/异常处理。实际任务开始前，执行者完整阅读；多agent由一级/二级读取并将本阶段适用规则明确下发，角色会话至少读取对应阶段和授权/异常规则，不必加载无关阶段。通用安全与首次配置仍见[总入口](../SKILL.md)。

以下默认结果路径针对普通实验；用户明确仅留远端、选择调优版本或组合/排除阶段时，以本次授权为准，并按[工程规范](project-contract.md)和[调优归属](autotuning.md)验收，不能冒称本地已回收。

## 用户口令与完成边界

部署镜像尚未由用户明确指定/授权AI选择时，先由execute列出现有相关镜像并给建议，经调度交主Agent请用户选择。按common-operations镜像规则执行；用户已经选定的同一镜像不在每阶段重复询问，切换或新增拉取仍须对应授权。

用户使用下列简写时严格按对应边界执行，不擅自扩大或缩小范围：

- “部署一下”：完成服务启动、健康检查和真实 `chat_test`；以 chat test 成功为本阶段终点，不自动运行 benchmark 或 profiling。
- “替换框架源码/替换算子/两者同时替换”：先确认具体文件、角色和服务重启范围，只准备用户实际要求的framework或operator变体；确实同时修改两类时才准备combined，并对所选版本验证真实加载和chat，不为凑四种模式额外重启baseline。修改前原件必须先冻结，成功后交design回收原/修改文件及修改说明，真实验证结果写正式报告；详细验证记录按需留远端，不默认新增本地SOURCE_MODIFICATION_VALIDATION.md。只改Skill/模板的请求不授权远端替换或重启；是否做性能测试及最后保留哪个版本由用户确定。
- “配置/框架/算子自动调优”：按已有Profiler/Nsys分析提出具体建议，结合当前版本官方调优指南生成联合方案；在确认范围内自动修改设计表和隔离源码、构建、chat_test，再对一个联合候选跑一套已确认benchmark，与可比基线对比并生成AUTOTUNING_REPORT.md。基线缺失、目标/预算/约束不明先问；用户明确只到chat时不跑benchmark，标收益未验证。不因只提出分析建议自动进入调优。
- “压测”：运行当前项目定义的 benchmark，等待本轮所有计划档位结束，解析并保存当前压测结果；不自动运行 profiler。
- 首次基线保留完整并发1、2、4、8、16、32；优化调试/联合调优使用tuning模式，仅测1、8、32并逐档与完整基线相同C比较。只缩减候选覆盖档位，不改每档负载协议或永久修改完整CONCURRENCIES；缺失/不可比基线先确认补测，不把三档结果当全档验证。
- “profiler”或“跑一下 profiler”：先确认是否同时生成 PyTorch 原生 `key_averages` 算子聚合表，再运行适配当前平台的原生Profiler，验证预期rank/角色与设备事件。NVIDIA回收原始trace、窗口摘要、日志和元数据；Ascend/torch_npu还须按profiling Skill原样回收整个`profile-output/`（深路径可用tar），并保留可读的rank结果。均归入本地`profiling_results/profiler/C<C>/`。不运行 Nsys，不自动分析。
- “profiling”或“跑一下 profiling”：依次完成 PyTorch Profiler 和 Nsys 采集，把两类结果复制到本地对应 `profiling_results/` 子目录；采集本身不等于分析。
- “nsys”或“跑一下 nsys”：只运行 Nsys 采集并把本轮 `.nsys-rep`、日志和必要元数据复制到本地 `profiling_results/nsys/C<C>/`；不重复运行 PyTorch Profiler，不自动分析。
- “项目结束”或“项目暂停”：停止并删除这个实验在所有目标主机上创建且可由配置/`LOG.md` 准确追溯的全部 server、router、client、benchmark、profiler 和 Nsys 容器及仍存的相关进程；验证设备与端口已释放，但不删除项目文件、模型、镜像、bind mount、结果目录或其他任务对象。该口令本身授权清理本实验对象，不授权处理归属不明或他人的对象。
- “分析一下 profiler 结果”：只分析已有 PyTorch Profiler 结果，analyze在远端写入分析，design再回收本地 `profiling_results/ANALYSIS.md` 的 PyTorch Profiler 部分；缺少结果时报告缺口，不自动重新采集。
- “分析一下 nsys 结果”：加载并遵循 `../profiling/nsight-systems/SKILL.md`，只分析已有 Nsys 结果，analyze在远端写入分析，design再回收本地 `profiling_results/ANALYSIS.md` 的 Nsys 部分；缺少结果时报告缺口，不自动重新采集。
- “分析一下瓶颈”或“分析一下 profiling 结果”：先执行 PyTorch Profiler 结果分析，再加载 `nsight-systems` Skill 执行 Nsys 结果分析，最后在同一 `ANALYSIS.md` 汇总交叉证据、瓶颈结论和待验证项；不把推断写成事实。

若用户显式组合、排除或改变范围，以用户当次表述为准。每个阶段只在其完成边界全部满足后宣告成功；已有合格产物可以复用，但必须核对它属于当前实验和所需运行。

### 每阶段的完成回复

收到每个阶段口令后，在执行前根据实际工程规模给出预计耗时区间和主要影响因素，并把估计、开始时间及依据写入 `LOG.md`。估计必须结合模型加载时间、节点/角色数量、TP/rank、workload 长度与档位、采集窗口、是否生成原生算子聚合、已有缓存以及现场资源，不能照搬固定时长。长任务若明显超出区间，主动更新估计并说明原因。

预计单个连续步骤超过 5 分钟时，启动前必须让用户选择后续方式，不能代替用户默认决定：

- **AI 接管查询**：将步骤作为可脱离会话的后台任务启动，记录任务 PID/作业 ID、日志、退出状态文件和结果目录；首次及后续每次状态检查的计划等待时间均不得超过15分钟，即取“预计需要等待的时间”和15分钟中的较小值，不能因总耗时较长而一次等待30分钟或更久。每次唤醒只做一轮有针对性的状态检查；确认仍正常运行后记录进度，再等待最多15分钟进行下一次检查，不在同一次唤醒中循环轮询、循环健康检查或持续读取日志。状态无实质变化时保持安静；完成、失败、停滞、明显超时或需要用户选择时及时汇报，并按新证据修正估计。监测配置的定时触发间隔同样不得超过15分钟；实际调度延迟导致超限时如实说明，不能声称严格按时检查。当前产品没有可用的延迟唤醒能力时，明确说明此选项不可用，不能假装已经安排。
- **人工唤醒**：将步骤按相同要求在后台启动，立即汇报当前状态、任务标识、日志/结果位置、预计剩余时间及建议用户多久后回来；此后不主动查询、不创建自动唤醒，等待用户再次发消息。

询问时用简洁语言说明两者区别和各自预计时间。用户已在当前指令中明确选择时不重复询问；否则未获得选择前不启动该长步骤。若原预计不超过 5 分钟的前台步骤意外超过阈值，在能安全转为后台时先保留现场，再让用户选择上述后续方式；不能继续高频查询。

预计不超过 5 分钟的步骤可以前台等待，但仍避免无意义的高频查询。多个长步骤串行时沿用用户已对本任务明确选择的接管方式，只有尚未选择或实际条件改变时才询问；不得因为后台运行而跳过资源预检、错误报告、完成验收或 `LOG.md` 记录。

阶段成功、失败或由用户停止时，都报告“执行前预计耗时、实际耗时、偏差原因”。每次得到可比较的预估和实耗后，按[平台经验与预测改进规则](../platforms/README.md)检查预测方法是否需要修正，有证据时提出具体Skill修改建议并等用户批准；本次计时本身不授权修改共享规则或写入平台耗时经验。实际耗时从本阶段第一次实质动作计到完成边界、失败点或停止确认，不把此前其他阶段的等待混入。完成回复最后列出的每个合理下一步都附一个基于当前工程状态的预计耗时区间；未知条件会显著改变时间时，明确写出待确认因素，不给虚假精确值。

每完成一个用户口令，回复必须先给成功/失败结论，再给本阶段最核心的产物，不用大量过程文件淹没用户：

本节的配置摘要、预计/实耗、证据链接和下一步属于对话汇报与内部记录，不能整段复制进正式报告。正式报告独立遵循delivery-report.md：按已开展流程实时维护完整实际代码/命令和结果，不引用其他文档补步骤，不预写未开展章节。

- 部署：先给出本次使用的用户可编辑设计表 `experiment.toml` 的本地回收路径和来源（复用既有文件、精确官方配置，或授权范围内试跑的迁移候选）；再用简洁参数表汇报模型/检查点、镜像与框架版本、部署拓扑、角色规模与设备数、TP/DP/EP/PP、模型后端/量化/推测解码与 draft model、关键显存比例、prefix/KV cache、chunked prefill 等设计参数及相对官方配置或迁移依据的适配。IP、端口、容器名、路径和设备编号不作为设计摘要，除非它们正在造成错误或冲突。仅汇报已知或启动输出已显示的生效值；未知且不影响当前阶段的内部默认项可省略，不为补齐参数摘要推迟启动或完成汇报。最后给出真实 chat test 的输入、核心回复、模型名、成功判据和 正式报告准确路径。
- 压测：先用最简洁语言说明本轮如何压测，包括 endpoint、ISL/OSL、并发档位、每档请求数、预热、dataset、tokenizer、prefix cache 状态和使用设备数；再给核心结果表及已写入结果的 正式报告路径。原始日志只在异常或用户要求时列出。
- Profiler：汇报C、预热2、预运行/采集时长、实际控制区间和请求数、P/D覆盖及batch、TP/rank、聚合选择与控制端点；列核心混合trace路径及ANALYSIS状态。
- Nsys：先用相同粒度说明 workload、角色、采集窗口和 Nsys capture range，再列出应在 NVIDIA Nsight Systems 中打开的核心 `.nsys-rep` 本地路径，并给出同一 `ANALYSIS.md` 路径及当前状态；CSV、SQLite、日志和 stats 不是 GUI 主文件。
- 分析 Profiler/Nsys/综合瓶颈：给出核心结论、对应 `ANALYSIS.md` 的准确路径，并再次指出支撑结论、需要人工打开核对的 trace 或 `.nsys-rep`。
- 优化实验：按“本次策略→效果百分比表→结果分析”主动简报。三层策略各一短句；逐档列吞吐/平均TTFT/平均TPOT/已采集尾延迟变化及成功数，2–3句点明总体好坏、代价与关键限制；不只给报告链接、不贴长命令或复述全文。附报告路径、预计/实耗和一条可选下一步/估时，详见`autotuning.md`。
- 项目暂停/结束：列出已停止并删除的本实验容器/进程、设备与端口释放验证，以及明确保留的本地工程和结果路径。

多机结果的一级主机目录表示文件来源机器，不表示 GPU；TP/rank 才表示并行进程或设备角色。`server/` 保存服务角色生成的原始采集文件，`client/` 保存发起 workload 的请求结果。完成回复只列真正用于打开或复核的文件；无 trace 的影子角色目录、临时中转、PID 文件和重复元数据不列为核心产物。相同目录下连续 rank 的文件可以用“目录 + 明确文件名/TP 范围”紧凑表达，但不能只给模糊的结果根目录。

完成回复最后给出符合当前阶段的可选下一步，简要说明现有能力，但不能倒退推荐已经完成且当前无需重做的阶段：部署后可选压测、Profiler、Nsys 或完整 profiling；压测后可选采集；Profiler 后优先建议分析 Profiler 或补采 Nsys；Nsys 后优先建议分析 Nsys，若两类结果齐全则建议综合瓶颈分析；完成单项分析后根据仍缺的证据建议补采/分析另一类结果或做综合分析。不要把下一步写成已经自动开始的新任务。

## 缺失参数与异常处理

本规则覆盖整个Skill及关联脚本的全部阶段：缺少运行环境、解释器、软件、系统工具、Python包、动态库、插件、模型/tokenizer文件、数据集或其他外部资源时，先只读确认并向用户说明用途、缺失证据、阻塞范围、拟安装/下载位置、来源以及对现有环境的影响，取得用户明确同意后才安装、下载、升级、替换或创建环境。“继续”“完成任务”不自动授权新增依赖；已明确批准的依赖与目标环境无需重复询问，新增范围仍需确认。不得因工具提示推荐安装就直接执行。

模型下载的首选来源例外已明确规定：原HF模型直接使用ModelScope，不先尝试HF或hf-mirror。已有模型下载授权且目标目录明确时，由对应execute执行，不因采用此默认来源再次索取换源批准；精确检查点/版本缺失则报告，不默默换模型。规则见[common-operations](operations/common-operations.md#模型下载execute负责优先modelscope)，不将此偏好扩大为自动安装下载工具或下载其他依赖的授权。

采集环境与离线验收/分析环境可以分离。用户指定运行环境时先检查该环境的解释器、依赖、报告访问权限和工具兼容性，并按指定环境执行；工具固定要求另一解释器时先说明冲突并询问，不静默切换、另建环境或向容器注入包。具体机器、环境名称和路径只写当前工程配置或LOG，不固化到通用Skill。

用户固定的实验语义、授权资源和工作负载不得擅改；实现启动的技术选择按根Skill“部署优先”自行处理。部署中的实现参数可在既有授权内按平台参考和框架默认自行选择、遇错修正；用户固定的对比/采集协议参数则从以下来源保持确定值：用户当次明确输入、已填写并校验的工程/实验配置、与精确检查点及当前版本匹配的官方命令，或不含策略选择的确定性推导。

- Profiler/Nsys默认只采一个中间time窗口：预热2后持续最多C个在途，完成4×C正式请求后采capture_seconds（默认15秒），停止采集后继续完成至少C请求再结束负载；不固定N=5C，不采initial/after-prerun。可选最短预运行时间默认0秒。P/D步数仅事后统计，max_requests触顶即失败；single保留混合trace，PD并发控制P/D端点，默认不采Router GPU。

- 开始部署、benchmark、PyTorch Profiler、Nsys、结果分析或清理前，列出该阶段必需输入并检查是否齐全。只有缺少用户意图或无法定位目标/确定授权范围时才询问。部署技术参数可沿用现有配置、参考命令与框架默认；无精确教程时在授权资源内选择合理迁移候选直接试跑，不把可由AI判断的技术设置变成用户必填项。
- 每次运行 PyTorch Profiler 都必须确认是否生成 native `key_averages`；用户当次已经明确开启或关闭时视为已确认，不重复询问。询问时同时说明：关闭聚合只生成 trace 与窗口摘要，完成较快，之后仍可用 Perfetto 和项目分析脚本离线分析时间线、kernel、通信、空闲与负载；开启聚合会在 profiler 进程退出前额外生成 PyTorch 原生 CPU/CUDA 算子累计时间、调用次数与均值表，口径最准确但可能显著增加内存和结束等待时间。原生 `key_averages` 只能在 profiler 对象仍存活时计算；从已导出的 trace 离线重建只能得到近似统计，不能声称等同原生口径。两个选项都要给出基于本次规模和历史记录的预计总时长或额外时长。
- benchmark、Profiler 和 Nsys 的 tokenizer 固定使用容器内已挂载模型检查点的 `MODEL_PATH`，不得用服务暴露名触发网络解析，也不为此重复询问。若该目录缺少 tokenizer 必需文件或无法读取，按异常流程报告并等待用户决定，不能自动联网下载或切换来源。
- 本地 tokenizer 不代表 workload 已完全离线。执行前按对应 benchmark/profiling Skill 核对当前版本的模型配置与 dataset 实现是否还会隐式联网；发现依赖时必须在正式请求或采集窗口开始前停止，让用户选择提供路径、授权 AI 下载到明确位置、配置网络/缓存或取消，不能自行更换 dataset 或生成替代数据。
- 出现错误、配置冲突、依赖/网络/权限问题、产物不完整或官方资料与现场不一致时，先用只读检查收集足以说明问题的证据。执行现场由execute向直属调度报告关键错误与影响；本次授权内的技术修正按下一条执行，不要求每次用户决定。只有新增依赖、改变用户固定语义/数据源、扩大拓扑/资源或影响他人时才经一级确认；不得借修复反复猜改或越权停止对象。
- 若问题只有一个不会改变实验语义、资源占用或他人任务的机械修复，execute可在本任务授权内自行定位、用隔离副本试修并验证；成功后把最小补丁及验证摘要经二级交design固化远端真源并封存新版本。新增依赖/下载、改变语义、长时间验证或扩大影响仍先向用户说明并取得相应同意。可逆的只读诊断、日志读取和状态核对无需额外确认。
- 已在缺参或异常状态下误启动的运行立即停止其后续动作，明确标为无效/未完成，不纳入正式结果；保留日志与产物作为证据，除非用户明确要求删除。


## 异常通知时点

发现现场与预期不符、资源冲突、失败/中断、权限/网络/下载阻塞、无效产物或显著超时，立即按三级→直属二级→一级上报已确认事实与影响，一级及时告知用户；不等完整根因、证据表或修复方案。完整证据随后补齐，涉及他人对象或超范围的操作仍先获批准；独立任务可继续且不影响通知义务。原生上报路由失效时采用multi-agent/shared.md的一次最小越级异常通知，不以静默低通信规则压住异常。
